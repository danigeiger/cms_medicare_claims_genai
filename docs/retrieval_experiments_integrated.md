- Top-1: no change

- Top-3: +10 percentage points

### Observation
Repeating the label did not improve Top-1 accuracy, but it improved

Top-3 and Top-5 retrieval.

Some individual variables improved substantially. For example,

`RNDRNG_PHYSN_NPI` moved from rank 3 to rank 1, while

`PRNCPAL_DGNS_CD` moved from rank 5 to rank 2.

Other variables became worse, showing that label emphasis alone does

not completely solve the ranking problem.

semantic search.

## Experiment 3 — Retrieval-Augmented Generation (RAG)
**Embedding model:** `sentence-transformers/all-MiniLM-L6-v2`

**Reranking model:** `cross-encoder/ms-marco-MiniLM-L-6-v2`

**Generative model:** `gpt-4.1-mini`

**Evaluation set:** 20 natural-language CMS variable queries

### Pipeline
1\. Chroma retrieves the five most semantically similar CMS codebook documents.

2\. The CrossEncoder reranks those five candidates.

3\. `rag.py` formats the retrieved documents into context for the LLM.

4\. GPT-4.1-mini identifies and explains the most relevant CMS variable.

### Results
- Correct answers: 19/20

- Preliminary accuracy: 95%

### Comparison With Previous Experiments
\| Method | Top-1 / Answer Accuracy |

\|---|---:|

\| Baseline retrieval | 60% |

\| Label emphasis | 60% |

\| CrossEncoder reranking | 80% |

\| Full RAG | 95% |

### Observation
The RAG pipeline identified the expected CMS variable in 19 of 20 generated answers.

Four questions that were not ranked first by the CrossEncoder were answered correctly by the LLM:

- `ADMTG_DGNS_CD`

- `ICD_PRCDR_CD25`

- `LINE_PLACE_OF_SRVC_CD`

- `RNDRNG_PHYSN_SPCLTY_CD`

This suggests that the LLM can identify the correct variable from multiple retrieved candidates even when the CrossEncoder does not rank it first.

### Failure Analysis
**Question:** What is the patient's race?

**Expected variable:** `BENE_RACE_CD`

**Result:** Incorrect

The LLM reported that the retrieved context contained physician identifier variables rather than information about beneficiary race.

This suggests a failure in the retrieval stage rather than an unsupported answer generated by the LLM.

### Evaluation Limitation
The current evaluation checks whether the expected CMS variable identifier appears anywhere in the generated response.

This can overestimate accuracy if the LLM mentions the correct variable but ultimately recommends a different one.

A stricter evaluation will extract the model's selected variable and compare it directly against the expected identifier.

### Next Steps
- Implement structured LLM output for more reliable evaluation.

- Investigate the failed `BENE_RACE_CD` retrieval.

- Test additional questions and ambiguous CMS terminology.

- Measure consistency across repeated evaluations.

### Conclusion
The full RAG pipeline achieved 95% preliminary accuracy on the 20-question evaluation set, compared with 80% Top-1 accuracy after CrossEncoder reranking and 60% for baseline semantic retrieval.

These results suggest that LLM-based generation can improve CMS variable identification when supplied with multiple relevant codebook documents.

## Experiment: Reciprocal Rank Fusion (RRF)
### Objective
Evaluate whether combining Chroma vector similarity rankings with CrossEncoder reranking improves retrieval performance for the CMS Medicare Claims GenAI system.

The experiment was motivated by a failure in the existing RAG pipeline: the question "Where was the service performed?" returned an incorrect variable despite Chroma initially retrieving the expected variable in first position.

### Experimental Setup
**Dataset:** CMS Medicare FFS Claims Codebook, containing 302 parsed variables.

**Evaluation set:** 20 natural-language questions, each paired with an expected CMS variable.

**Embedding model:** `sentence-transformers/all-MiniLM-L6-v2`

**Reranking model:** `cross-encoder/ms-marco-MiniLM-L-6-v2`

**Retrieval configuration:**

- Chroma retrieves the top 20 candidates.

- CrossEncoder reranks the 20 candidates.

- RRF combines the two rankings using a smoothing constant of `k = 60`.

- Top-1, Top-3, and Top-5 accuracy are calculated against the expected variable.

The experiments were implemented in:

- `src/retrieval/experiment_rrf.py`

- `src/retrieval/evaluate_rrf.py`

### Results
\| Retrieval Strategy | Top-1 Accuracy | Top-3 Accuracy | Top-5 Accuracy |

\|---|---:|---:|---:|

\| Chroma | 60% (12/20) | 90% (18/20) | 100% (20/20) |

\| CrossEncoder | **75% (15/20)** | 90% (18/20) | 95% (19/20) |

\| Reciprocal Rank Fusion | 70% (14/20) | **100% (20/20)** | **100% (20/20)** |

### Failure Analysis: Place of Service
**Query:** "Where was the service performed?"

**Expected variable:** `LINE_PLACE_OF_SRVC_CD`

The original Chroma retrieval ranked the expected variable first. However, the CrossEncoder demoted it to sixth place, excluding it from the five candidates provided to the language model.

\| Strategy | Expected Variable Rank |

\|---|---:|

\| Chroma | 1 |

\| CrossEncoder | 6 |

\| RRF | 1 |

RRF restored the expected variable to the top five.

However, the expected variable and `CLM_SRVC_FAC_ZIP_CD` received equal RRF scores. Their first-place ordering was determined by the stable sorting behavior of Python, rather than a meaningful difference in their fusion scores.

This illustrates an important limitation: the original question is ambiguous between the type of service setting and the geographic location of a service facility.

### Query Sensitivity
Three alternative phrasings were evaluated:

\| Query | CrossEncoder Rank | RRF Rank |

\|---|---:|---:|

\| Where was the service performed? | 6 | 1 |

\| What is the place of service code for a claim line item? | 1 | 1 |

\| What type of setting was the medical service performed in? | 12 | 7 |

The CrossEncoder performed substantially better when the question closely matched terminology in the codebook.

This suggests that the reranking model may be sensitive to terminology and query phrasing, potentially reducing performance for users unfamiliar with CMS vocabulary.

### Interpretation
The CrossEncoder achieved the highest Top-1 accuracy (75%), while RRF achieved the highest Top-3 accuracy (100%).

Chroma and RRF both achieved 100% Top-5 accuracy. RRF therefore recovered the expected variable lost by CrossEncoder reranking without reducing Top-5 coverage on this benchmark.

Because the RAG system provides five retrieved candidates to GPT-4.1-mini, Top-5 accuracy is especially relevant.

However, improved retrieval coverage does not necessarily translate into improved final-answer accuracy.

### Limitations
- The benchmark contains only 20 questions.

- The evaluation questions were reused during experimentation, so these results do not demonstrate generalization to unseen queries.

- Some natural-language questions have multiple plausible interpretations.

- Equal-weight RRF does not resolve ties between conflicting rankings.

- The experiment evaluates retrieval accuracy, not the final answers generated by the language model.

### Conclusion and Next Steps
RRF is a promising alternative to CrossEncoder-only ranking, achieving 100% Top-3 and Top-5 retrieval accuracy on the existing benchmark.

The current production-style pipeline remains unchanged pending end-to-end evaluation.

**Next experiment:** Compare the existing Chroma → CrossEncoder → GPT-4.1-mini pipeline against Chroma → RRF → GPT-4.1-mini using the same evaluation questions and structured exact-match scoring.

A larger, independently constructed evaluation set should also be developed to assess performance on unseen natural-language questions.

## Experiment: End-to-End RAG Evaluation with RRF
### Objective
Determine whether the improved retrieval accuracy from Reciprocal Rank Fusion (RRF) translates into more accurate final answers from GPT-4.1-mini.

### Experimental Setup
Two RAG pipelines were evaluated using the same 20 CMS codebook questions:

- **Baseline:** Chroma → CrossEncoder → GPT-4.1-mini

- **Experimental:** Chroma → CrossEncoder + RRF → GPT-4.1-mini

Both pipelines used the same language model, instructions, structured output schema, and five retrieved context documents.

**Evaluation metric:** Exact-match accuracy between the predicted CMS variable identifier and the expected variable.

**Evaluation script:** `src/rag/evaluate_rrf_rag.py`

### Results
\| Pipeline | Correct Answers | Accuracy |

\|---|---:|---:|

\| CrossEncoder + GPT-4.1-mini | 19/20 | 95% |

\| RRF + GPT-4.1-mini | 20/20 | **100%** |

RRF improved end-to-end accuracy by 5 percentage points on the existing benchmark.

### Error Analysis
The only difference in final-answer correctness occurred for the question:

**"Where was the service performed?"**

Expected variable: `LINE_PLACE_OF_SRVC_CD`

- CrossEncoder pipeline predicted `CLM_SRVC_FAC_ZIP_CD`.

- RRF pipeline correctly predicted `LINE_PLACE_OF_SRVC_CD`.

The baseline reranker placed the expected variable sixth, excluding it from the five documents passed to GPT-4.1-mini.

RRF placed the expected variable first, allowing the language model to select it.

### Interpretation
The experiment demonstrates that retrieval-stage improvements can translate into better final-answer accuracy.

RRF achieved 100% Top-5 retrieval accuracy and 100% end-to-end exact-match accuracy on the 20-question benchmark.

However, the evaluation set is small, and its questions were used during retrieval development. These results do not establish performance on unseen questions.

Additionally, the service-location question has multiple plausible interpretations, and RRF produced tied scores for the place-of-service and facility-ZIP variables.

### Conclusion
RRF outperformed the CrossEncoder-only pipeline on the existing end-to-end benchmark without introducing additional incorrect answers.

RRF is the preferred candidate for further development, subject to validation on a larger, independent evaluation set.

**Next steps:**

1\. Refactor retrieval to avoid duplicate Chroma queries.

2\. Integrate RRF into the RAG pipeline while retaining the CrossEncoder baseline.

3\. Evaluate both pipelines on unseen natural-language questions.

## Experiment: Exact Vector Search as a Diagnostic Reference

### Objective

Investigate an intermittent failure observed for the query **"What is the patient's race?"**, where the expected variable `BENE_RACE_CD` was sometimes absent from Chroma's retrieved candidates. Determine whether the failure originated in the query embedding, stored vectors, or indexed search.

### Method

- Used the existing `sentence-transformers/all-MiniLM-L6-v2` model and persisted `cms_codebook` collection containing 302 variables.
- Confirmed the query embedding was consistent across independent Python processes.
- Verified that the stored embedding for `BENE_RACE_CD` matched its regenerated embedding.
- Compared Chroma's indexed `collection.query()` results with exhaustive NumPy squared Euclidean distance calculations over every stored embedding.
- Implemented `retrieve_exact()` in `src/retrieval/retrieval.py`, preserving a Chroma-compatible result structure and leaving the original `retrieve()` function intact.

### Results

For the race query, exhaustive NumPy search consistently placed `BENE_RACE_CD` first in the diagnostic runs. Chroma sometimes ranked it first but, in other fresh processes, omitted it from its top 20 results. Retrieving all stored embeddings using `collection.get()` did not resolve the discrepancy in a failing process.

### Interpretation

The evidence isolates the observed discrepancy to the indexed retrieval path, rather than to an absent CMS variable or a changing query embedding. **The precise cause within ChromaDB has not been established.** HNSW approximate search, persisted index state, and process-dependent index loading remain hypotheses, not confirmed diagnoses.

## Experiment: ChromaDB vs. Exact NumPy Retrieval Accuracy

### Objective

Determine whether exhaustive search changes baseline semantic retrieval accuracy on the existing 20-question benchmark.

### Method

Compared `retrieve()` and `retrieve_exact()` with 20 candidates per question, using the same embedding model, stored vectors, distance metric, and expected variable identifiers.

**Evaluation script:** `src/retrieval/evaluate_exact_vs_chroma.py`

### Results

| Metric | ChromaDB indexed search | Exact NumPy search |
|---|---:|---:|
| Top-1 accuracy | 60% (12/20) | 60% (12/20) |
| Top-3 accuracy | 90% (18/20) | 90% (18/20) |
| Top-5 accuracy | 100% (20/20) | 100% (20/20) |
| Differences in full top-20 rankings | 0 | Reference |

### Interpretation

Both approaches produced identical rankings in this particular run. Exact search does not inherently improve the semantic quality of the embeddings; its value here is as an exhaustive reference and a way to avoid approximate-neighbor omissions. A single matching run does not rule out intermittent differences.

## Experiment: Cross-Process Retrieval Reliability

### Objective

Quantify how frequently Chroma's indexed retrieval disagrees with exact NumPy search when started in fresh Python processes.

### Method

Executed **10 independent Python processes**. Each process evaluated the same 20 natural-language questions with both methods and compared the full top-20 result lists.

**Evaluation script:** `test_retrieval_reliability.py`

### Results

| Measure | Result |
|---|---:|
| Successful processes | 10/10 |
| Question comparisons | 200 |
| Full-ranking disagreements | 10/200 (5%) |
| Comparisons where Chroma omitted the expected variable from its top 20 while exact search found it | 1 |

The consequential omission occurred in **run 9**:

| Query | Expected variable | Chroma rank | Exact NumPy rank |
|---|---|---:|---:|
| What is the patient's race? | `BENE_RACE_CD` | Not in top 20 | 1 |

The other nine disagreements did not change the expected variable's rank in their respective questions, although some positions elsewhere in the top-20 lists differed.

### Interpretation

The reliability test reproduced the earlier failure under controlled comparisons. In this sample, Chroma's results differed from exhaustive search in 5% of question comparisons; **this is an observed sample rate, not an established long-run failure probability**. Because a reranker can only reorder retrieved candidates, omission of the correct variable at the first stage cannot be repaired by the downstream CrossEncoder or RRF using those same candidates.

## Experiment: End-to-End Retrieval Ranking With Exact Search and RRF

### Objective

Test whether substituting exhaustive NumPy candidate selection preserves or improves downstream CrossEncoder + RRF retrieval accuracy.

### Method

Compared two **retrieval-ranking pipelines**, each using 20 initial candidates:

1. ChromaDB indexed retrieval → CrossEncoder → RRF.
2. Exact NumPy retrieval → CrossEncoder → RRF.

Both used the existing 20-question evaluation set and `calculate_rrf()` implementation. No language-model answer generation was performed in this experiment.

**Evaluation script:** `src/retrieval/evaluate_pipeline_comparison.py`

### Results

| Metric | Chroma + RRF | Exact NumPy + RRF |
|---|---:|---:|
| Top-1 accuracy | 70% (14/20) | 70% (14/20) |
| Top-3 accuracy | 100% (20/20) | 100% (20/20) |
| Top-5 accuracy | 100% (20/20) | 100% (20/20) |

### Interpretation

Both retrieval-ranking pipelines achieved identical accuracy in this run. Compared with the 60% Top-1 initial retrieval baseline measured in the same phase, CrossEncoder + RRF increased Top-1 accuracy to 70%. The intermittent Chroma omission did not occur during this particular comparison, so the run alone does not measure the reliability advantage of exact search.

**Important distinction:** The earlier *End-to-End RAG Evaluation with RRF* measured **GPT-4.1-mini's final answers** (20/20 exact matches in that run). This experiment measures **retrieval ranks only**, not generated answer accuracy. The two results should not be treated as interchangeable.

## Updated Findings and Engineering Decision

The experiments now distinguish three separate performance concerns:

1. **Semantic relevance:** Label emphasis, CrossEncoder reranking, and RRF affect how relevant CMS variables are ranked.
2. **Candidate-selection reliability:** Chroma's indexed search intermittently omits a variable that exhaustive search ranks first.
3. **Answer correctness:** The language model's final selected CMS variable must be evaluated separately from retrieval rankings.

For the current **302-variable, 384-dimensional** collection, exact NumPy search is the **proposed default for candidate selection**, while ChromaDB remains the persistent store for embeddings and metadata. The original indexed retrieval function remains available for comparison. This is a proposed integration decision, **not a claim that the main RAG pipeline has already been switched**.

### Remaining Work

- Integrate `retrieve_exact()` into the main RAG pipeline without changing the stored embeddings, CrossEncoder, or RRF logic.
- Benchmark retrieval latency and memory use; exhaustive search is practical at this scale but should not be assumed efficient for much larger collections.
- Rerun end-to-end GPT-4.1-mini evaluation after integration using structured exact-match scoring.
- Develop a larger, independently constructed test set, including paraphrases and ambiguous queries, to assess generalization.
- Keep the intermittent Chroma behavior documented without claiming an unverified internal root cause.

### Overall Conclusion

The project evolved from basic embedding similarity into a multi-stage RAG retrieval system with empirical accuracy and reliability testing. The central engineering lesson is that **a strong reranker or language model cannot compensate for a relevant document that never enters the candidate set**. Exact retrieval offers a testable way to improve candidate-selection dependability for this small codebook, while the separate answer-generation evaluation remains essential for assessing the final system.

## Current Implementation and Final Development Evaluation — October 12, 2026

### Implemented RAG pipeline

The main `src/rag/rag.py` pipeline now uses the following sequence:

1. Embed the natural-language question with `sentence-transformers/all-MiniLM-L6-v2`.
2. Use `retrieve_exact()` in `src/retrieval/retrieval.py` to rank all **302 stored CMS variables** by NumPy squared Euclidean distance and return the top **20**. ChromaDB remains the persistent source of the stored embeddings, documents, and metadata.
3. Use `rerank_candidates()` and `cross-encoder/ms-marco-MiniLM-L-6-v2` to rerank those **same 20 candidates**, without issuing a second retrieval query.
4. Use `calculate_rrf()` with reciprocal rank fusion to combine the exact-search and CrossEncoder rankings, then pass the top **five** documents to GPT-4.1-mini.
5. Return a Pydantic `CMSAnswer` containing `variable`, `label`, and `explanation`; score the predicted variable using exact identifier matching.

The indexed Chroma `retrieve()` function remains available for diagnostic comparison; the main RAG path uses `retrieve_exact()`. The application loads `OPENAI_API_KEY` from the local `.env` file via `load_dotenv()`. Secrets are not included in version control.

### Limitations and next experiments

- All reported 20-question evaluations used a small development benchmark that influenced the pipeline and question wording; performance on unseen questions remains unknown.
- Earlier experiments using the original ambiguous service-location question are preserved above as historical observations; they are not directly comparable to results on the revised question.
- Exact NumPy retrieval avoids approximate-neighbor omissions for this small stored collection but does not improve the semantic meaning of embeddings. The internal root cause of intermittent Chroma indexed-search discrepancies remains unverified.
- Benchmark retrieval latency and memory requirements before scaling beyond the current 302-variable collection.
- Construct a larger, independent holdout with paraphrases, ambiguity cases, and unsupported questions; compare alternative pipelines on identical questions under controlled conditions.
